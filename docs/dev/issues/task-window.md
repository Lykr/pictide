# 两个在途生图任务（已确认、已实现）

## 架构

沿用 Application → Task → GenerationBackend / Store；候选和推荐不参与调度。Task 将当前单任务改为全应用最多两个在途任务的提交窗口，不按后端数量倍增。复用现有 ComfyUI 队列、事件订阅和 HTTP 核对；不增加线程、服务、HTTP API、前端选项或依赖。

两个在途任务通常为一个正在出图、一个在 ComfyUI 排队；Pictide 不要求 ComfyUI 同时执行两个工作流。POST 提交本身仍顺序完成，第二项不必等第一项出图。

## 调用与数据流

1. 启动恢复已有提交记录，然后从 Store 取得在途任务和可补入窗口的排队任务。
2. 每个新任务独立建立事件订阅，复用 claim_job → submit → attach_prompt。两项分别持有适配器、prompt_id 和状态，收到任一结束通知都可核对，不以第一项是否完成阻挡第二项结果处理。
3. 窗口不足两个且有任务时立即补位；尚未提交的手动任务优先于漫游。已经提交到 ComfyUI 的顺序不重排，因此手动任务可能等待已经投喂的一项漫游任务。
4. HTTP 确认后端结束后释放提交窗口，先补入下一项，再沿原路径下载、保存图片与提示词 JSON、完成入库。保存一张图片期间，ComfyUI 可继续执行已排队的下一项。
5. 各任务继续使用自己的配置快照与请求标识，结果按任务关联。事件仅唤醒，不直接代表成功；健康连接每 30 秒兜底，断线或旧任务按 2 秒核对。空队列等待现有通知。
6. 当前漫游最多两个未完成任务的准备额度不变；准备速度不足时允许窗口空缺，不额外增加漫游投喂循环。

## 模块接口与存储

Store 增加：

```python
def dispatch_jobs(self, limit: int = 2) -> list[dict]: ...
# 返回当前在途任务，以及按手动优先、创建时间选出的可补位任务。
# 已存在的在途任务全部恢复，不因窗口已满而漏掉结果；超出时不再新增。

def finish_dispatch(self, iid: str) -> None: ...
# 仅确认该任务已不占用后端窗口，不改变图片保存结果或取消状态。
```

Task 改用上述队列查询；原 next_job 单条查询移除。GenerationBackend 接口沿用已实现的 start_events / events_connected / stop_events / submit / inspect / cancel / image，无新增适配器接口。Task 对 Application、Host 的接口及现有 HTTP/SSE 字段不变。

jobs 增加内部布尔字段 backend_pending（默认 0），区分后端是否仍占用窗口与图片是否已保存：claim_job 时置 1；后端确认结束、确定拒绝提交或确认删除排队任务后清 0。attach_prompt、recover_submissions 恢复已有已接受任务的占用标记。原图、任务、喜欢及偏好保留，发布前备份；不增加历史迁移工具或兼容层。

取消与异常：

- 未提交任务直接取消；已在 ComfyUI 排队且确认删除成功的任务释放窗口。
- 无法移除的运行任务保持取消状态并继续占用窗口，直到 HTTP 确认结束；不调用全局 interrupt。此标记持久化，重启后也不会因为取消状态丢失占用信息。
- 提交结果不确定时保持待核对与窗口占用，继续使用既有 request_id 复核，不自动重提；明确的提交失败释放窗口。历史已存在的 unknown 不追溯占位。
- 单个任务查询失败不妨碍另一个任务核对；保存失败保留原失败处理，不重复生成。

## 验证与发布

只做少数隔离冒烟：第一项未完成时第二项已提交且第三项未提交；任一项结束后先补位、即使图片下载仍等待；手动优先、结果关联、取消不超投、重启恢复与不确定提交不重试。模拟 HTTP/WebSocket 和临时 SQLite，不提交真实 GPU 测试任务。发布前备份并提前告知 Pictide 后端重启。

实现验证：新增 5 个 Task 隔离冒烟和 3 个 Store 隔离冒烟，覆盖两个在途上限、任一槽位完成后先补位再下载、手动优先、取消占位、重启恢复、提交不确定不重提、慢查询不阻塞另一项补位，以及补位异常不会丢失已完成结果。复用事件、交接、漫游准备、取消确认和分页的相关用例；不运行全量测试，不提交真实 GPU 任务。

已完成结果在释放窗口前记入 Task 的待保存集合；补位异常仍尝试保存，临时内部保存异常保留结果稍后重试。退出中断时，由持久化 prompt_id 与 running 状态在下次启动恢复 HTTP 核对及图片保存。此集合属于 Task 内部状态，没有新的模块接口或后台循环。
